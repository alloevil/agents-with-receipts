# 003 — 跨进程 grep 输出当契约，上游改一行日志下游静默断裂

- 日期：2026-08
- 适用范围：任何 agent 工具；一切"父进程解析子进程 stdout"的架构
- 证据：[alloevil/weibo-chat-auto@5ccf368](https://github.com/alloevil/weibo-chat-auto/commit/5ccf368)（修复）、[141bf53](https://github.com/alloevil/weibo-chat-auto/commit/141bf53)（沉淀成模块+测试）

## 症状

大版本重构后用户点"同步"，得到一句毫无信息量的「归档器异常退出（code 1）」。真实原因（凭据失效，需要重新扫码）明明就在子进程输出里。

## 根因

Web 服务用 `spawn` 拉起归档器，靠 grep 子进程 stdout 判断结果。重构改掉了归档器的打印格式和退出码语义，服务端的解析约定**整套失配**且无人察觉：

1. 凭据失效从"exit 0 + 特定文案"改成了"exit 1"——检测分支只在 exit 0 时跑，永远不再命中；
2. 成功计数 grep 的标志串 `已保存到:` 已被删除——**每次成功同步都会报成"归档 0 个群"**；
3. "被跳过的群"分支成了死代码。

这套字符串契约横跨两个进程、散落在 HTTP handler 内部、没有任何测试。上游一动，下游只能靠用户报障发现。

## 修复

把全部输出解析抽成独立模块 `lib/sync-report.js`——它是解释归档器打印格式的**唯一地点**。测试输入直接用真实事故日志的同构串（凭据失效块、重试序列取最后一条错误、SIGKILL 无错误行、按群头计数），格式再变测试即红。

## 沉淀

- 新模块 100% 行覆盖；`AGENTS.md` 明确一句：「改归档器输出格式要同步改 `lib/sync-report.js` 和它的测试」
- 附带一条通用手法：修复时先用一次性脚本对真实日志验证解析正则，**验证脚本随手扔掉之前，把它变成正式测试**——这次事故的检测逻辑第一版就只验证过一次性脚本，没沉淀，一周后另一处又断了

## 通用教训

跨进程/跨组件的字符串契约（日志格式、CLI 输出、错误文案）是最容易被 agent 和人同时忽略的接口。要么提炼成"唯一解析模块 + 用真实样本做输入的测试"，要么换成结构化输出（JSON line / 退出码语义表）。散在调用点的 `out.includes('...')` 一定会在某次重构里静默断裂。
